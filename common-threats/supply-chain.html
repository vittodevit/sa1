Software Supply Chain Attacks and Dependency Confusion

A supply chain attack does not attack the victim directly. Instead, the attacker hides malicious code inside software, libraries or updates that the victim already trusts. One successful attack can reach thousands of companies at the same time.

What is the software supply chain?

Almost no program is written from zero. Developers use many packages (libraries) written by other people, downloaded from public registries like npm (JavaScript) or PyPI (Python). The software is then built on a server and sent to users as an update. If an attacker changes any of these steps, the malicious code reaches all the users.

Common types of supply chain attacks

  • Compromised build: the attacker enters the company and changes the software while it is being built.
  • Hijacked package: the attacker takes control of a popular package and publishes a malicious version.
  • Typosquatting: a fake package with a name very similar to a real one, hoping that someone makes a typing mistake.
  • Dependency confusion: explained below.

Dependency confusion

Companies often have private packages that exist only on their internal server. Some installation tools look for packages both on the private server and on the public registry, and choose the one with the highest version number .

  1. The attacker finds the name of a private package, for example company-utils .
  2. The attacker publishes a package with the same name on the public registry, with a very high version ( 99.0.0 ).
  3. The company's tool sees two packages and installs the public one, because its version is higher.
  4. The malicious code runs inside the company.

In 2021 the researcher Alex Birsan used this technique (with harmless code) to run code inside more than 35 companies, including Apple, Microsoft and PayPal.

Famous examples

Famous supply chain attacks
Year Name What happened
2020 SolarWinds Attackers put a backdoor in an update of the Orion software, used by many companies and US government agencies.
2022 PyTorch A fake torchtriton package on PyPI was installed instead of the real one by users of the nightly version (dependency confusion).
2024 xz utils A contributor gained trust for years and then hid a backdoor in a compression library used by Linux systems.

How to defend

  • Give private packages a scope (for example @company/utils ) linked only to the private server.
  • Use lock files (for example package-lock.json ) that save the exact version of every package.
  • Check the name, the author and the number of downloads before installing a package.
  • Keep a list of all the components used in the software (SBOM).
  • Verify where a package comes from, using signatures and frameworks like SLSA.
